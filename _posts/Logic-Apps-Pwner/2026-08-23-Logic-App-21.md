> **TL;DR** — A user with read-only access to an Azure Key Vault (but no permission to directly read secrets) had write access to a Logic App workflow. By editing the workflow to add an Azure Key Vault connector, the Logic App's own connection permissions were abused to retrieve a secret the user's identity could not access directly.

## Scenario

Sometimes the compromised user can have permission to edit the Logic App workflow. Let's log into the Azure Portal using the credentials provided and start enumerating. On enumerating the account, we find the user has **read permissions on the Key Vault** and **read/write permissions on the Logic App workflow**. Abuse this write permission to add a Key Vault action and exfiltrate a secret (flag) from Azure Key Vault.

---

## Overview

### What is a Logic App Workflow?

A Logic App workflow is a visual representation and implementation of a business process or integration scenario in Azure Logic Apps. It defines the steps, actions, and conditions that are executed in a specific sequence to automate a particular workflow.

### Why Does Write Access to a Logic App Matter Here?

A Logic App workflow executes using its own configured connections — which may have broader permissions than the identity editing the workflow. If a user can edit the workflow but not directly read a secret in Key Vault, they can insert a new action into the workflow that performs the read on their behalf, then surface the result back to themselves (e.g., via an HTTP response).

This lab targets **Azure Key Vault** — a centralized service used to store secrets, keys, and certificates. The attack pattern remains identical to other Logic App abuse scenarios: **permission delegation through automation**.

> 💡 **Hint:** Make use of the Key Vault connector action. The permission gap is between the user's identity and the Logic App's Key Vault connection permissions.

1. Select an **available connection** to authenticate with the Key Vault
2. Specify the **secret name** by:
   - Clicking the **drop-down** at the right end of the input field
   - Selecting the **name of the secret** to retrieve

The Logic App will now attempt to fetch the secret using its own configured connection identity.

### Step 5 — Surface the Output via Response Action

1. Open the **Response** action (the HTTP response trigger output)
2. In the **Body field**, click **"Add dynamic content"**
3. Select the **secret value** from the dynamic content options

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **Write access to the workflow bridged the permission gap** | The user's identity couldn't read the secret directly, but the Logic App's own Key Vault connection could — editing the workflow let the user borrow that access. |
| 2 | **The Key Vault connector's connection was more privileged than the user** | This is the core of the abuse: a service connection with broader rights than the identity managing it. |
| 3 | **The Response action was the exfiltration path** | Without wiring the secret value into the HTTP response, the data would have remained internal to the workflow run. The Response action made it visible to anyone with the trigger URL. |
| 4 | **No direct secret-read permission was ever granted to the user** | The entire flag retrieval happened without the user's own identity ever reading the secret — all access was proxied through the Logic App's Key Vault connection. |
| 5 | **HTTP trigger exposes secret content without authentication** | The "When a HTTP request is received" trigger in Logic Apps is typically public-facing, allowing anyone with the URL to trigger the workflow and receive its output, including secret values. |
| 6 | **Key Vault "read" access is not the same as "get secret" access** | Being able to view a Key Vault's metadata or configuration does not necessarily mean the identity can read secret values — but a Logic App's own connection can bypass that distinction entirely. |

---

## Impact

- **Privilege Escalation:** Write access to a Logic App becomes equivalent to secret-read access on every Key Vault the Logic App can connect to.
- **Data Exfiltration:** Sensitive secrets, keys, and connection strings stored in Azure Key Vault can be extracted if the Logic App has access to them.
- **Unauthorized Operations:** The Logic App's connections can perform actions (list, get, or even set secrets) on behalf of the editing user, beyond the user's own permissions.

---

## Impact in a Real-Time Environment

### 🔴 Privilege Escalation via Workflow Editing
Any identity with write access to a Logic App can insert new actions that leverage the Logic App's own connections — effectively inheriting permissions the identity does not hold directly. This is a **transitive trust** issue: the Logic App is trusted by its connections, and editing the Logic App transfers that trust.

### 🔴 Sensitive Secret Exposure via Key Vault
In this lab, the Logic App's Key Vault connector exposed a secret value. In production, the same technique could expose:
- Database connection strings and credentials
- API keys and service principal secrets
- TLS/SSL certificates and private keys
- Third-party integration tokens
- Encryption keys used to protect other sensitive data

### 🟠 Silent Abuse With No Direct Resource Access Logs
Because the abuse happens entirely through the Logic App's connections, it may not appear in the audit logs of the Key Vault under the attacking user's identity — complicating detection and forensics.

### 🟠 Reusable Attack Pattern Across Any Connector
This is not limited to Key Vault. **Every connector available in Logic Apps** could be added the same way if the Logic App's connection has access to it — creating multiple exfiltration and lateral movement paths.

### 🟠 Public-Facing HTTP Triggers
Public-facing HTTP triggers on Logic Apps often require no authentication, allowing any user with the trigger URL to invoke the workflow and receive its output — potentially including secrets, keys, or certificates.

### 🟠 Key Vault Access Policies Often Overly Permissive
Key Vault access policies or RBAC role assignments are frequently scoped too broadly (e.g., "Key Vault Contributor" instead of a narrowly scoped custom role), especially on connections used by automation tools like Logic Apps.

---

## Why We Need to Secure This

**1. Write Access to a Logic App Is Effectively Access to Its Connections**
Granting "Contributor," "Logic App Contributor," or workflow-edit rights on a Logic App implicitly grants the ability to use every connection already configured on that Logic App — regardless of the editor's own permissions on those underlying resources.

**2. Connections Are Often More Privileged Than Necessary**
Logic App connections to Key Vault are frequently set up with broad "get," "list," and "set" permissions for convenience during development and never scoped down before reaching production.

**3. The Attack Requires No Specialized Tooling**
This entire exploitation happened inside the Azure Portal's built-in Designer UI — no external scripts, tools, or APIs required. Any user with basic Azure Portal access can execute this attack.

**4. HTTP Triggers Are Inherently Unauthenticated**
By default, "When a HTTP request is received" triggers in Logic Apps have no built-in authentication, making them ideal for exfiltrating secrets to an external attacker or an attacker's own session.

**5. Key Vault Is a High-Value Target**
Key Vault often centralizes the most sensitive secrets in an environment. A Logic App with broad Key Vault access effectively becomes a single point of failure for the secrets it can reach.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Restrict Workflow Edit Access** | Limit who can edit Logic App workflows separately from who can view run history or trigger them. Treat edit access as equivalent to direct access on every resource the Logic App's connections can reach. Use role-based access control (RBAC) with granular roles like "Logic App Contributor" (edit workflows) vs. "Reader" (view only). |
| 🪪 **Scope Key Vault Connections to Least Privilege** | Configure Key Vault connections with the minimum access needed — e.g., "get" on a specific secret rather than "list/get/set" access to the entire vault. Use fine-grained access policies or Azure RBAC scoped to individual secrets where possible. |
| 📁 **Separate Key Vaults by Sensitivity** | Isolate highly sensitive secrets into dedicated Key Vaults with stricter access controls, rather than storing all secrets in one shared vault accessible by multiple Logic Apps. |
| 🎯 **Use Managed Identity Per Logic App** | Prefer Managed Identity connections scoped via RBAC at the resource level over shared connection strings or broadly-scoped service accounts. Assign each Logic App its own managed identity with a custom role for least-privilege access. |
| 🔌 **Authenticate and Authorize HTTP Triggers** | If the Logic App's HTTP trigger outputs sensitive data, require authentication (e.g., Azure AD OAuth, API Key) on the trigger itself. Avoid public-facing triggers for workflows that handle secrets. |
| 📊 **Monitor Workflow Edits** | Enable diagnostic logging on Logic App changes and alert on new actions/connectors being added, especially by identities without direct access to the Key Vault. Correlate Logic App edit events with subsequent secret access in Key Vault audit logs. |
| 🔍 **Periodically Review Configured Connections** | Audit each Logic App's connections against the actual permissions required by its business function, removing unnecessary access. Document why each connection is needed and what secrets it should access. |
| 📋 **Establish Approval Workflows for Edits** | For production Logic Apps, require approval before workflow edits are deployed, especially if they involve new connectors or actions on Key Vault. |
| 📋 **Enable Key Vault Logging and Alerting** | Turn on diagnostic logs for Key Vault and alert on unexpected "GetSecret" operations, particularly those originating from Logic App connections rather than direct user activity. |

## How This Helps During Incident Response

- **Workflow version history shows exactly what changed.** Logic Apps retain versions of the workflow definition — comparing versions quickly reveals when and what action was added, and by whom.

- **Run history reveals what data was accessed.** The Key Vault action's run history shows the exact secret name accessed, the timestamp, and (depending on logging configuration) the operation performed, scoping the extent of data exposure.

- **Connection audit logs identify the true accessor.** Since the read happens via the Logic App's connection rather than the user's identity, incident response teams should correlate Logic App run timestamps with Key Vault audit logs — not just user identity logs — to see the full picture.

- **Trigger URL analysis.** Check if the Logic App's HTTP trigger URL was accessed by unexpected users or external IPs. If so, the workflow was invoked externally, and any secret content in the Response action was exposed to those IPs.

- **Secret access timeline.** Correlate Logic App run times with Key Vault "GetSecret" audit logs to determine exactly which secrets were read and when.

- **Improved IR playbooks.** This pattern should prompt responders to check Logic App edit history whenever investigating:
  - Unexpected secret access in Key Vault
  - Cases where the accessing identity shows no direct "get secret" permissions on that resource
  - Any unusual Logic App run activity
  - Potential lateral movement from a compromised user account
