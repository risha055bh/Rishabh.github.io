> **TL;DR** — A Logic App configured with a **Recurrence trigger** (rather than a manual HTTP trigger) meant the workflow itself could not be invoked on demand to leak data. Instead, the user's direct read/write access to the connected **Storage Account** was enough to enumerate blob **version history**, where an older version of a blob contained a sensitive flag no longer present in the current version.

## Scenario

In certain scenarios, a Logic App can be triggered in multiple ways, and the way it is triggered can reveal sensitive data through the resources it touches — not just through the workflow itself. Leverage this information to obtain the flag from the blob.

---

## Overview

### What is a Logic App Workflow?

A Logic App workflow is a visual representation and implementation of a business process or integration scenario in Azure Logic Apps. It defines the steps, actions, and conditions that are executed in a specific sequence to automate a particular workflow.

### Why Does the Trigger Type Matter Here?

Unlike previous labs where an HTTP-triggered Logic App could be manually invoked to exfiltrate data through a crafted Response action, this Logic App uses a **Recurrence trigger** — meaning it runs automatically on a schedule and cannot simply be triggered on demand via a public URL.

However, this doesn't close off the attack path. If the compromised identity already has **direct read/write access to the Storage Account** the Logic App uses, the attacker doesn't need to go through the Logic App at all — they can go straight to the storage layer and look for sensitive data left behind in **blob version history**.

> 💡 **Hint:** Recurrence trigger in place — look beyond the workflow itself, into what the Logic App's connected storage account exposes directly.

## Steps to Reproduce

### Step 1 — Enumerate Access

Log in to the Azure Portal using the provided credentials and enumerate available resources:
- The user has **read and write access** to the Storage Account
- The Logic App associated with this storage account uses a **Recurrence trigger** (not manually invokable via HTTP)

### Step 2 — Enumerate the Storage Blob

1. Navigate to the **Storage Account**
2. Open the relevant **Container**
3. Locate a blob containing a welcome message
4. Inspect the blob for additional properties — specifically, check whether **blob versioning** is enabled

### Step 3 — Review Blob Version History

On further enumeration, the blob is found to have **multiple versions** retained. Each version represents a prior state of the blob's content before it was overwritten.

### Step 4 — Inspect Each Blob Version

For each version listed:
- **Option A:** Select the version and click **"Make current version"** to promote it and view its content directly
- **Option B:** Click the **three-dot menu (⋯)** at the right end of the blob version entry and choose **Download** to inspect its content locally without altering the blob

### Step 5 — Locate the Flag

After checking all available blob versions, one older version is found to contain a flag that is **not present in the current version** of the blob.

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **Recurrence-triggered Logic Apps can't be abused via a public HTTP endpoint** | Unlike HTTP-triggered workflows, there was no trigger URL to invoke on demand — forcing the attack to pivot to a different resource. |
| 2 | **Direct storage account access made the Logic App irrelevant to the attack path** | The user's own identity already had read/write access to the Storage Account, so the Logic App itself wasn't needed to reach the data. |
| 3 | **Blob versioning retained historical, sensitive content** | The current version of the blob was "clean," but an older version still contained a flag — showing that overwriting a blob does not remove sensitive data if versioning is enabled. |
| 4 | **"Make current version" and "Download" both expose historical content** | Either action allows an attacker to view retired blob content without needing to modify anything permanently (using Download), or by temporarily promoting an old version. |
| 5 | **No Logic App interaction was required at all** | This lab illustrates that Logic App security is only one part of the picture — the underlying connected resources need to be secured independently. |

## Impact

- **Data Exposure via Version History:** Previous versions of blobs can retain sensitive data long after the "current" version has been sanitized or updated.
- **Bypasses Logic App Trigger Restrictions:** Even when a Logic App is not exploitable due to its trigger type, direct access to its underlying resources can still lead to data exposure.
- **Expanded Attack Surface from Versioning Features:** Enabling blob versioning without a retention/cleanup policy increases the amount of historical sensitive data available to an attacker.

---

## Impact in a Real-Time Environment

### 🔴 Sensitive Data Left in Blob Version History
Organizations often update or "clean" a blob's current content (e.g., removing secrets, credentials, or PII that were mistakenly uploaded) without realizing that **older versions remain fully accessible** to anyone with read access, if blob versioning is enabled.

### 🟠 Trigger Type Is Not a Security Control
Assuming a Logic App is "safe" because it uses a Recurrence trigger instead of an HTTP trigger is a false sense of security — the underlying connected resources may still be directly reachable by the same identity, independent of the Logic App entirely.

### 🟠 No Special Tooling Required
Like other labs in this series, this entire exploitation was performed using only the Azure Portal UI — no external tools, scripts, or APIs were needed.

### 🟠 Versioning Without Governance Increases Risk
Blob versioning is a valuable feature for recovery and auditing, but without a clear data governance policy (e.g., soft-delete retention limits, periodic purging of old versions containing sensitive data), it can silently retain sensitive information indefinitely.

### 🟠 Broad Storage Account Permissions
A user or service principal with read/write access at the Storage Account level can browse every container, blob, and version within it — permissions that are often granted more broadly than necessary.

---

## Why We Need to Secure This

**1. Blob Versioning Retains History, Not Just the Present**
Any sensitive data ever written to a blob — even briefly — can remain permanently recoverable if versioning is enabled and old versions are never purged.

**2. Direct Resource Access Bypasses Logic App-Level Controls**
Securing the Logic App's trigger type or connectors does nothing to protect data if the same identity already has direct access to the underlying Storage Account.

**3. "Current Version" Is Not the Same as "Only Version"**
Teams that sanitize or rotate blob content often assume the sensitive data is gone once the current version is updated — but historical versions may still expose it.

**4. Least Privilege Applies to Storage Accounts Too**
Read/write access at the Storage Account level should be scoped down to specific containers or even specific blobs where possible, rather than granted broadly.

**5. Versioning and Soft-Delete Settings Are Often Overlooked**
Many teams enable blob versioning for resiliency purposes without considering its implications for data exposure and long-term secret retention.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Scope Storage Account Access Tightly** | Grant read/write access at the container or blob level using Azure RBAC or SAS tokens with limited scope, rather than account-wide Contributor/Reader roles. |
| 🗑️ **Establish a Blob Version Retention Policy** | Configure lifecycle management rules to automatically delete old blob versions after a defined retention period, minimizing the window during which sensitive historical data remains accessible. |
| 🧹 **Purge Sensitive Data From All Versions, Not Just Current** | When sanitizing a blob that previously contained sensitive data, explicitly delete the affected historical versions — updating only the current version is not sufficient. |
| 📁 **Separate Sensitive Data Into Dedicated Containers** | Store sensitive or regulated data in containers with stricter access controls and monitoring, separate from general-purpose or low-sensitivity blobs. |
| 📊 **Enable Storage Account Diagnostic Logging** | Turn on logging for blob read, list, and version-access operations, and alert on unusual access to blob version history. |
| 🔍 **Audit Logic App Trigger Types and Connected Resource Permissions Together** | Don't evaluate Logic App security in isolation — review the permissions of every identity that has direct access to resources the Logic App also touches. |
| 📋 **Periodically Review Versioning and Soft-Delete Configuration** | Confirm that blob versioning, if enabled, aligns with an active data governance and retention policy rather than being left on indefinitely by default. |

## How This Helps During Incident Response

- **Blob version timestamps establish a timeline.** Each blob version is timestamped, allowing responders to reconstruct exactly when sensitive content was introduced and when it was overwritten or removed from the "current" version.

- **Storage Account access logs identify who accessed which version.** Diagnostic logs (when enabled) reveal which identities listed, downloaded, or promoted specific blob versions — critical for scoping the extent of exposure.

- **Version history review should be standard practice.** When investigating a suspected data leak involving Blob Storage, responders should always check version history, not just the current blob content, since sensitive data may persist in a version no longer visible by default.

- **Correlate with Logic App activity separately.** Since this attack path did not require any Logic App interaction, IR teams should treat storage account access logs and Logic App run logs as **independent evidence sources** — a clean Logic App run history does not rule out data exposure via direct storage access.

- **Improved IR playbooks.** This pattern should prompt responders to check blob version history whenever investigating:
  - Data exposure incidents involving Blob Storage
  - Identities with broad Storage Account-level permissions
  - Cases where a "sanitized" blob is suspected to have leaked data prior to cleanup
