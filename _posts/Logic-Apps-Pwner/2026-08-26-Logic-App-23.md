> **TL;DR** — A Logic App configured with a **Sliding Window trigger** writes data to a Storage Account blob on a recurring schedule, but only *after* the trigger has actually fired at least once. A user with read/write access to the Storage Account found an empty blob on first inspection — the flag only appeared once the sliding window trigger executed and populated the blob a few minutes later.

## Scenario

In certain scenarios, a Logic App can be triggered in multiple ways, and the way it is triggered can reveal sensitive data through the resources it touches — not just through the workflow itself. The goal here is to **leverage this information to obtain the flag from the blob**.

---

## Overview

### What is a Logic App Workflow?

A Logic App workflow is a visual representation and implementation of a business process or integration scenario in Azure Logic Apps. It defines the steps, actions, and conditions that are executed in a specific sequence to automate a particular workflow.

### Why Does the Trigger Type Matter Here?

This Logic App uses a **Sliding Window trigger** — a recurrence-based trigger type that processes data in fixed, non-overlapping time intervals, unlike a simple Recurrence trigger which just fires on a schedule regardless of data state. Because the trigger runs on its own interval, any data it writes downstream (in this case, to a Storage Account blob) will **only exist after the trigger has actually fired at least once**.

This means the timing of enumeration matters: checking the target blob too early — before the Logic App's trigger has run — can make the target look empty or uninteresting, when in fact the sensitive data simply hasn't been written yet.

## Steps to Reproduce

### Step 1 — Log in to the Azure Portal

Log in to the Azure Portal using the provided credentials and enumerate available resources. On enumeration, the user is found to have **read-write permissions on the Storage Account**.

### Step 2 — Enumerate the Storage Blob

Check the Storage Account for anything of interest. On enumeration, a blob is found containing a welcome message.

### Step 3 — Review the Blob's Initial State

On further enumeration, the blob is found to contain **one version**. Checking that version at this point does **not** reveal any sensitive data or flags.

After waiting approximately **6–8 minutes**, the blob content is checked again. This time, the flag is present — the Sliding Window trigger in the underlying Logic App had not fired yet during the initial check, so the flag had not been written to the blob at that point.

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **The blob appeared empty on first inspection** | Without understanding the trigger type in play, an analyst might conclude the target is a dead end and move on, missing the flag entirely. |
| 2 | **Sliding Window triggers write data on their own schedule** | Unlike an HTTP trigger that can be invoked on demand, a Sliding Window trigger only produces output when its interval elapses — patience (or re-checking) is required. |
| 3 | **No Logic App interaction was required to retrieve the flag** | As with other trigger-based labs in this series, direct read/write access to the Storage Account was sufficient — the Logic App workflow itself never needed to be touched or triggered manually. |
| 4 | **Re-checking a "clean" resource after a delay is a valid enumeration technique** | This lab reinforces that a negative result during initial enumeration doesn't necessarily mean a resource is not exploitable — some misconfigurations only manifest after time-based automation runs. |

## Impact in a Real-Time Environment

### 🟠 Time-Delayed Data Exposure via Automation Output
Sliding Window and other schedule-based triggers can silently write sensitive data — logs, processed records, reports — to storage resources at intervals. If access controls on the destination storage are too permissive, this data becomes exposed the moment it's written, regardless of whether the Logic App itself is ever directly accessed.

### 🟠 False Negatives During Security Assessments
Point-in-time enumeration (a single scan or check) can miss time-delayed data exposure entirely. An assessment that checks a storage resource once and finds nothing may falsely conclude the resource is safe, when a scheduled process later populates it with sensitive content.

### 🟠 No Special Tooling Required
As with other labs in this series, this entire exploitation was performed using only the Azure Portal UI and a bit of patience — no external tools, scripts, or APIs were needed.

### 🟡 Broad Storage Account Permissions
A user or service principal with read/write access at the Storage Account level can browse every container and blob within it, including ones later populated by unrelated scheduled automation — permissions that are often granted more broadly than necessary.

---

## Why We Need to Secure This

**1. Trigger Type Does Not Reduce the Sensitivity of the Data Produced**
Whether a Logic App uses an HTTP, Recurrence, or Sliding Window trigger has no bearing on how sensitive the data it eventually writes might be — the trigger only affects *when* that data appears.

**2. Direct Resource Access Bypasses Logic App-Level Controls**
Securing the Logic App's trigger type or connectors does nothing to protect data if the same identity already has direct access to the underlying Storage Account the Logic App writes to.

**3. Time-Based Automation Can Create Moving Targets**
Security reviews that treat a resource's state as static can miss exposure windows created by scheduled processes — a blob that was empty during an audit may not stay that way.

**4. Least Privilege Applies to Storage Accounts Too**
Read/write access at the Storage Account level should be scoped down to specific containers or blobs where possible, independent of what any connected Logic App is doing.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Scope Storage Account Access Tightly** | Grant read/write access at the container or blob level using Azure RBAC or SAS tokens with limited scope, rather than account-wide Contributor/Reader roles. |
| 📁 **Separate Sensitive Data Into Dedicated Containers** | Store output from scheduled Logic App processes in containers with stricter access controls and monitoring, separate from general-purpose or low-sensitivity blobs. |
| 📊 **Enable Storage Account Diagnostic Logging** | Turn on logging for blob read, write, and list operations, and alert on unexpected access shortly after scheduled Logic App runs. |
| 🔍 **Audit Logic App Trigger Types and Connected Resource Permissions Together** | Don't evaluate Logic App security in isolation — review the permissions of every identity that has direct access to resources the Logic App writes to, regardless of trigger type. |
| ⏱️ **Account for Time-Based Exposure in Security Reviews** | When assessing storage resources tied to scheduled automation, verify state both before and after expected trigger intervals rather than relying on a single point-in-time check. |
| 📋 **Periodically Review Configured Connections** | Audit each Logic App's connections against the actual permissions required by its business function, removing unnecessary access. |

## How This Helps During Incident Response

- **Blob timestamps establish a timeline.** Comparing blob creation/modification timestamps against the Logic App's trigger schedule helps responders determine exactly when sensitive data was written and whether it correlates with a scheduled run or something anomalous.

- **Storage Account access logs identify who accessed the blob and when.** Diagnostic logs (when enabled) reveal which identities listed or downloaded the blob, and whether that access happened before or after the trigger populated it with sensitive content.

- **Correlate with Logic App run history separately.** Since this attack path did not require any Logic App interaction, IR teams should treat storage account access logs and Logic App run logs as **independent evidence sources** — a clean Logic App run history does not rule out data exposure via direct storage access.

- **Improved IR playbooks.** This pattern should prompt responders to check both storage access logs and Logic App trigger schedules whenever investigating:
  - Data exposure incidents involving Blob Storage tied to Logic App output
  - Identities with broad Storage Account-level permissions
  - Cases where a resource appeared "clean" during an initial check but was later found to contain sensitive data
