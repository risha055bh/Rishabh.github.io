# Logic App 24 — Modify Workflow and Key Vault Version

> **TL;DR** — A user with write access to a Logic App workflow, but only read access to a Key Vault, abused the workflow to enumerate every historical **version** of a Key Vault secret rather than just its current value. By listing secret versions and then fetching each one individually, an older version containing the flag was recovered — even though the current secret value did not contain it.

## Scenario

In certain scenarios, a Logic App can be triggered in multiple ways, and the way it is configured can reveal sensitive data through the resources it touches — not just through the current state of a single secret. The goal here is to **leverage this information to obtain the flag from the Key Vault**.

---

## Overview

### What is a Logic App Workflow?

A Logic App workflow is a visual representation and implementation of a business process or integration scenario in Azure Logic Apps. It defines the steps, actions, and conditions that are executed in a specific sequence to automate a particular workflow.

### Why Does Write Access to a Logic App Matter Here?

A Logic App workflow executes using its own configured connections — which may have broader permissions than the identity editing the workflow. If a user can edit the workflow but only has read access to a Key Vault (not necessarily to every secret value or version within it), they can insert new actions into the workflow that enumerate and retrieve secret data on their behalf, then surface the result back to themselves via an HTTP response.

Unlike a simpler Key Vault abuse scenario that just fetches the **current** value of a secret, this lab requires going a step further: Key Vault retains a **version history** for each secret, and older versions may contain data — such as a flag or a legacy credential — that no longer exists in the current version.

## Steps to Reproduce

### Step 1 — Enumerate Access

Log in to the Azure Portal using the provided credentials, then search for **"Logic App"** in the search bar and select it. On enumerating the account, the user is found to have **read permissions on the Key Vault** and **read/write permissions on the Logic App workflow**.

### Step 2 — Open the Logic App Designer

Go to the Logic App and select **Logic App Designer** to view the workflow.

<img width="1540" height="941" alt="image" src="https://github.com/user-attachments/assets/efd80949-c0f7-4e8b-a7f0-273f0408da78" />


### Step 3 — Add an Azure Key Vault Action to List Secret Versions

1. Click the **+** button to insert a new step
2. Select **"Add an action"**
3. Search for **"Azure key vault"** in the search bar
4. Select **"Azure key vault"** from the connector options
5. Choose **"List secret versions"** from the available actions tab

<img width="1385" height="681" alt="image" src="https://github.com/user-attachments/assets/2c410b8c-482e-4490-ac03-a77c8eb57e34" />


**Why "List secret versions"?** This action reveals every historical version identifier for a given secret — information not visible from the Key Vault's default read-only view for this user.

### Step 4 — Configure the Secret Name

Specify the secret name by clicking the **drop-down** at the right end of the input field and selecting the name of the secret.

### Step 5 — Surface the Version List via Response Action

1. Open the **Response** action
2. In the **Body** field, click **"Add dynamic content"**
3. Select **"collection of secrets"**
4. **Save the workflow**

### Step 6 — Trigger and Retrieve the Version List

Copy the trigger URL from the **"When an HTTP request is received"** trigger and paste it into the browser. Sending the request returns a response containing the **versions** of the Key Vault secret. Note down these version identifiers for use in the next steps.

<img width="1907" height="123" alt="image" src="https://github.com/user-attachments/assets/ebdbc26c-8ca2-4f1c-bdca-16cf5aed2279" />


### Step 7 — Replace the Action to Fetch a Specific Secret Version

1. Go back to the Logic App and edit the workflow
2. Click the **menu (⋯)** at the top right corner of the "List secret versions" step and **delete** it
3. Add a new step in between by clicking **+** → **"Add action"**, as performed previously
4. From the actions tab, select **"Get secret version"**
5. Paste in one of the version numbers noted earlier

### Step 8 — Surface the Secret Value via Response Action

1. Open the **Response** action
2. Select the **Body** field, and from the dynamic content, select **"the secret"** to output the secret value in the response
3. **Save the workflow**

<img width="1882" height="857" alt="image" src="https://github.com/user-attachments/assets/62e37a4d-f465-4f67-abad-ef94d4364d1f" />


### Step 9 — Trigger and Iterate Through Versions

Copy the HTTP request trigger URL as performed previously and send the request. If the flag is not present in the response, repeat the process for the next noted version number — replacing the version in the "Get secret version" action each time. After iterating through the noted versions, the flag is found in one of the historical secret versions.

## Key Points During Flag Finding

| # | Observation | Why It Matters |
|---|-------------|-----------------|
| 1 | **Write access to the workflow bridged the permission gap** | The user's identity had only read access to the Key Vault at large, but the Logic App's own connection could enumerate and fetch specific secret versions — editing the workflow let the user borrow that access. |
| 2 | **The current secret version did not contain the flag** | This lab specifically required going beyond the "latest" value — reinforcing that a secret's current state does not represent its full history. |
| 3 | **"List secret versions" revealed an attack roadmap** | Enumerating all version identifiers up front turned a blind guessing exercise into a scoped, iterative one. |
| 4 | **The Response action was the exfiltration path each time** | Every iteration relied on wiring the fetched value into the HTTP response — without it, each attempt's result would have stayed internal to the workflow run. |
| 5 | **HTTP trigger exposes secret content without authentication** | The "When an HTTP request is received" trigger in Logic Apps is typically public-facing, allowing anyone with the URL to trigger the workflow and receive its output, including historical secret values. |
| 6 | **Iterative version fetching required repeated workflow edits** | Each version check required editing and re-saving the workflow, then re-triggering it — a manual but ultimately effective enumeration process entirely within the Portal UI. |

## Impact in a Real-Time Environment

### 🔴 Historical Secrets Remain Recoverable
Key Vault's versioning feature is designed for recoverability and auditing, but it also means that **any credential ever stored in a secret — even briefly — can remain retrievable** by anyone with sufficient Key Vault connector access, long after it was "rotated out."

### 🔴 Privilege Escalation via Workflow Editing
Any identity with write access to a Logic App can insert new actions that leverage the Logic App's own connections — effectively inheriting permissions the identity does not hold directly, including the ability to enumerate secret version history.

### 🟠 Legacy Credentials Increase Attack Surface
Older secret versions may correspond to legacy applications, deprecated service accounts, or credentials that were never fully decommissioned elsewhere — giving an attacker a foothold into systems assumed to be no longer accessible.

### 🟠 Silent Abuse With No Direct Resource Access Logs
Because the abuse happens entirely through the Logic App's connections, it may not appear in the audit logs of the Key Vault under the attacking user's identity — complicating detection and forensics.

### 🟠 Public-Facing HTTP Triggers
Public-facing HTTP triggers on Logic Apps often require no authentication, allowing any user with the trigger URL to invoke the workflow and receive its output — potentially including current or historical secret values.

---

## Why We Need to Secure This

**1. Write Access to a Logic App Is Effectively Access to Its Connections**
Granting "Contributor," "Logic App Contributor," or workflow-edit rights on a Logic App implicitly grants the ability to use every connection already configured on that Logic App — regardless of the editor's own permissions on the underlying Key Vault.

**2. Secret Versioning Needs an Active Lifecycle Policy**
Key Vault retains old secret versions indefinitely by default. Without a deliberate purge or rotation policy, every historical credential remains a live attack surface.

**3. The Attack Requires No Specialized Tooling**
This entire exploitation happened inside the Azure Portal's built-in Designer UI — no external scripts, tools, or APIs required. Any user with basic Azure Portal access and workflow-edit rights can execute this attack.

**4. HTTP Triggers Are Inherently Unauthenticated**
By default, "When an HTTP request is received" triggers in Logic Apps have no built-in authentication, making them ideal for exfiltrating secrets — current or historical — to an external attacker or an attacker's own session.

**5. "Get Secret" Is Not the Only Relevant Key Vault Permission**
Access reviews that only consider whether an identity can "get" the current secret value miss the broader risk posed by "list" and "get version" operations, which expose the entire secret history.

## Remediation

| Control | Action |
|---------|--------|
| 🔐 **Restrict Workflow Edit Access** | Limit who can edit Logic App workflows separately from who can view run history or trigger them. Treat edit access as equivalent to direct access on every resource the Logic App's connections can reach. |
| 🪪 **Scope Key Vault Connections to Least Privilege** | Configure Key Vault connections with the minimum access needed — avoid granting "list" and "get version" operations unless the workflow's business function genuinely requires historical access. |
| ♻️ **Purge Old Secret Versions on Rotation** | When rotating a secret, explicitly disable or purge outdated versions rather than leaving them indefinitely retrievable. |
| 🎯 **Use Managed Identity Per Logic App** | Prefer Managed Identity connections scoped via RBAC at the resource level over shared connection strings or broadly-scoped service accounts. |
| 🔌 **Authenticate and Authorize HTTP Triggers** | If the Logic App's HTTP trigger outputs sensitive data, require authentication (e.g., Azure AD OAuth, API Key) on the trigger itself. |
| 📊 **Monitor Workflow Edits and Key Vault Version Operations** | Enable diagnostic logging on Logic App changes and Key Vault access, and alert on "list secret versions" or "get secret version" operations originating from Logic App connections. |
| 🔍 **Periodically Review Configured Connections** | Audit each Logic App's connections against the actual permissions required by its business function, removing unnecessary access to secret version history. |
| 📋 **Establish Approval Workflows for Edits** | For production Logic Apps, require approval before workflow edits are deployed, especially if they involve new connectors or actions on Key Vault. |

## How This Helps During Incident Response

- **Workflow version history shows exactly what changed.** Logic Apps retain versions of the workflow definition — comparing versions quickly reveals when a Key Vault action was added, modified, or repeatedly edited (a signal of iterative enumeration, as performed in this lab).

- **Key Vault audit logs reveal version-level access.** Diagnostic logs for Key Vault show "list secret versions" and "get secret version" operations distinctly from simple "get secret" calls — a spike in version-specific requests from a Logic App connection is a strong indicator of this technique.

- **Correlate Logic App run timestamps with Key Vault access logs.** Since the read happens via the Logic App's connection rather than the user's identity, incident response teams should correlate Logic App run timestamps with Key Vault audit logs — not just user identity logs — to see the full picture.

- **Trigger URL analysis.** Check if the Logic App's HTTP trigger URL was accessed repeatedly by the same identity or IP in a short window — a pattern consistent with iterating through multiple secret versions.

- **Improved IR playbooks.** This pattern should prompt responders to check Logic App edit history and Key Vault version-access logs whenever investigating:
  - Unexpected secret access in Key Vault, especially involving historical versions
  - Repeated Logic App edits in a short time span
  - Cases where the accessing identity shows no direct "get version" permissions on that resource
  - Potential lateral movement from a compromised user account
